1. FLAKY TEST RISK ANALYSIS & MITIGATION ARCHITECTURE

In Lecture 07 (tr. 24-26), flaky tests undermine engineering confidence by passing or failing non-deterministically.
For VT-099, two primary sources of flakiness were identified and proactively mitigated:

A. Shared State Contamination (PostgreSQL DB):
- Risk: Concurrent or sequential tests mutating the shared `accounts`, `crawled_documents`, or `admin_audit_logs` tables
  can leak state across test boundaries, causing intermittent failures.
- Mitigation:
  * Strict fixture isolation (`cleanup_data` autouse fixture) runs both BEFORE and AFTER each test function.
  * Uses deterministic test-specific IDs (`55555555-5555-4555-8555-*`) and document prefixes (`doc_vt099_*`),
    ensuring other test suites running on the database are never affected.
  * Deterministic test user cleanup cascades cleanly to `auth_sessions` and `admin_audit_logs`.

B. Race Condition Timing Jitter (Barrier vs Sleep):
- Risk: Using `time.sleep()` for concurrency testing introduces timing jitter, CPU load sensitivity, and flaky CI execution.
- Mitigation:
  * TC-10 uses `threading.Barrier(2)` synchronization across two separate physical database connections (`admin_test_engine().connect()`).
  * Both worker threads block at the barrier before releasing simultaneously to compete for the `SELECT ... FOR UPDATE` row lock.
  * Zero reliance on wall-clock sleeps, guaranteeing 100% deterministic contention regardless of CPU scheduling speed.
