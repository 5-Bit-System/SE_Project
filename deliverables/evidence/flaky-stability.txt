1. FLAKY TEST RISKS ANALYSIS (LECTURE 07 TR.21)

According to Software Testing principles (Lecture 07 - Test Smells, Antipatterns, and Flakiness),
flaky tests produce non-deterministic results (passing and failing without code changes).
In VT-099, two primary flakiness categories were identified and rigorously mitigated:

--------------------------------------------------------------------------------
Risk 1: Shared Database State & Pollution (Trạng thái cơ sở dữ liệu dùng chung)
--------------------------------------------------------------------------------
Source of Flakiness:
- Tests mutate shared persistent tables (`accounts`, `crawled_documents`, `admin_audit_logs`).
- If a test leaves dirty state, duplicate primary keys, or uncommitted rows, subsequent tests or
  repeated runs fail intermittently depending on test execution order or leftover data.
Mitigations in VT-099:
- Idempotent Account Setup:
  `ensure_account()` executes `ON CONFLICT (id) DO UPDATE` to ensure test reviewer accounts
  (`REVIEWER_1_ID`, `REVIEWER_2_ID`, `GUEST_ID`) can be invoked across multiple runs without
  `UniqueViolation` errors while guaranteeing known credentials.
- Fixture-level Document Lifecycle Isolation:
  `sample_pending_doc` explicitly deletes any existing record with `doc_vt099_test_pending` before
  inserting a pristine pending document, and cleans it up upon fixture teardown.
- Independent Transactions:
  Each API request and service function operates within scoped transactions (`with eng.begin() as conn`),
  preventing lingering table-level lock states across tests.

--------------------------------------------------------------------------------
Risk 2: Concurrency Timing & Non-deterministic Multi-threading (Bất đồng bộ & Race Timing)
--------------------------------------------------------------------------------
Source of Flakiness:
- Multi-threaded concurrency tests often rely on arbitrary sleeps (`time.sleep(0.1)`), which fail
  flakily under variable CPU load, OS scheduling jitter, or slower disk I/O in CI environments.
Mitigations in VT-099:
- Synchronization via `threading.Barrier(2)`:
  In `test_tc10_service_concurrency_race_condition_barrier`, two worker threads are synchronized
  strictly at the barrier point (`barrier.wait(timeout=10)`). Neither thread proceeds until both
  threads are alive and ready to contend for the database record simultaneously.
- Pessimistic Row-level Locking (`SELECT ... FOR UPDATE`):
  Serializability is enforced at the database transaction layer via row locks and publication locks,
  guaranteeing that exactly one thread acquires the lock first and commits, while the contending
  thread is blocked until lock release and then deterministically encounters the CAS mismatch.
- Explicit Thread Joins with Timeouts:
  Threads are joined with explicit timeouts (`t.join(timeout=15)`), guaranteeing no hung threads or
  resource leakage even in failure conditions.
