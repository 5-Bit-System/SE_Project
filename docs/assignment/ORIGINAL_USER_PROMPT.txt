BT cá nhân 3 – AI-07 – VT-100
BỐI CẢNH CÁ NHÂN HÓA (VT-100)
Sinh viên: Thái Việt Trung — 23001946. Nhóm: SE2026-T25. Vai trò: Thành viên.
Dự án: “AI-07 – Explainable Course Recommender”.
Repository chính thức: https://github.com/5-Bit-System/SE_Project

Change request riêng: Thêm chức năng import dữ liệu hàng loạt; bản ghi lỗi không được làm mất các bản ghi hợp lệ.
Risk trọng tâm: thay đổi nhỏ làm hỏng một behavior cũ không liên quan.
Kỹ thuật thiết kế test bắt buộc: state transition testing.
Mutation/deliberate bug bắt buộc: đảo điều kiện true/false trong một business rule.
Mức tải kiểm chứng: 200 người dùng/tác vụ đồng thời; mục tiêu p95 không quá 5.0 giây.
Ràng buộc làm việc với AI: AI phải lập kế hoạch và nêu assumptions trước khi sinh code; bạn phải bác bỏ ít nhất một assumption sai.

YÊU CẦU THỰC HIỆN

1. Specification và AI-assisted plan (15 điểm)
- Chuyển change request thành: 01 problem statement, 3–5 acceptance criteria và ít nhất 2 non-functional constraints.
- Chỉ ra invariant/contract quan trọng nhất cần được bảo vệ.
- Dùng coding agent tạo implementation plan trước khi code. Ghi prompt, assumptions và các file agent dự định thay đổi.
- Review plan bằng repository thật; sửa hoặc bác bỏ ít nhất 2 điểm bằng evidence.

2. Test strategy dựa trên risk (20 điểm)
- Lập test strategy gồm unit, integration/API và E2E; nêu rõ test nào không cần thiết.
- Lập bảng tối thiểu 10 test cases: ID, risk/requirement, test level, precondition/input, expected result, priority.
- Bắt buộc áp dụng kỹ thuật “state transition testing”; giải thích cách chọn test data.
- Có ít nhất 2 negative tests và 1 failure-path test gắn với risk riêng.

3. Test-first AI-assisted implementation (25 điểm)
- Chọn một vertical slice nhỏ nhưng chạy được của change request.
- Tạo nhánh Git riêng; ghi commit ban đầu được dùng làm baseline.
- Viết hoặc sinh test để test thất bại đúng lý do trước khi sửa code; lưu evidence của lần fail.
- Dùng AI hỗ trợ tạo patch nhỏ; review diff trước khi chấp nhận. Không merge code không hiểu.
- Sau patch, chạy lại test và ghi evidence pass; nêu file/commit/PR liên quan.
- Nếu repository chưa đủ điều kiện triển khai change request, tạo executable test harness hoặc characterization test trên module gần nhất và giải thích giới hạn.

4. Đánh giá chất lượng test — “Who tests the tests?” (25 điểm)
- Đưa deliberate bug/mutation “đảo điều kiện true/false trong một business rule” vào một nhánh hoặc commit tạm thời, không để lại trong nhánh nộp bài.
- Chứng minh ít nhất một test phát hiện mutation. Nếu mutation sống sót, bổ sung/sửa test rồi chạy lại.
- Phân tích coverage: line/branch coverage nếu công cụ hỗ trợ, và risk coverage theo acceptance criteria. Không dùng tỷ lệ coverage đơn độc để kết luận chất lượng.
- Kiểm tra ít nhất 2 nguy cơ flaky test: time, order/shared state, network, concurrency hoặc random data.
- Thực hiện kiểm chứng tải ở mức 200 tác vụ đồng thời và so sánh với mục tiêu p95 5.0 giây; nếu không thể chạy tải thật, trình bày harness, dữ liệu giả lập và giới hạn kết luận.

5. Engineering evidence và reflection (15 điểm)
- Tạo traceability: Acceptance criterion/Risk → Test case → Test file → Commit/PR → Kết quả.
- Lập AI Usage Log: công cụ, prompt chính, output được dùng, thay đổi/bác bỏ và evidence.
- Chỉ ra 2 điểm AI-generated code/tests có vẻ hợp lý nhưng không đáng tin ngay.
- Viết reflection 250–350 từ: điều gì khiến confidence tăng lên, điều gì vẫn chưa được chứng minh và test tiếp theo có giá trị cao nhất.
