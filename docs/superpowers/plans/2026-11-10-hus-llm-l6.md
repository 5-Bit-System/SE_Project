# HUS LLM L6 Readiness and Rollback Plan

**Goal:** Make the conditional activation decision reviewable and prove rollback
returns the exact canonical response without calling a provider.
**Architecture:** A read-only CLI replays sealed L5 review evidence and checks current
code/source pins, real model use, facts/citations/coverage and reviewed improvement.
API integration tests exercise existing enable/disable behavior with mock HTTP.
An operator runbook explains process env/restart, UI consent and rollback scope.
**Tech Stack:** Existing Python/pytest/FastAPI/httpx, no new dependencies.
**Spec:** User-selected L6 row and L5 report; L5 currently fails DEV-Q025 completeness.
**Execution:** Native on hus-llm-rag, no commit/push/deploy/live calls or .env edits.

## Decisions and constraints

- Do not turn on defaults or bypass failed L5 content acceptance. Do not tune
  prompt/validator/source or rewrite historical evidence to obtain a green decision.
- Readiness is evidence assessment, not automatic production/operator sign-off.
  Even passing evidence requires manual acceptance and separate operational checks.
- Reuse L5 actual latency, actual model and separate used/fallback/token counts;
  synthetic rollback timings are not provider latency or semantic acceptance.
- Toggling a file or an unrelated shell cannot update the running server env.
  Runbook uses a dedicated restarted loopback process, Google HTTPS and server-only key.
- Existing requests may finish under the flag captured at their entry; document
  this scope rather than promise cancellation or total20s deadline.
- Keep source/retrieval/data/model/gold/old receipts and L1-L5 runtime/evaluators intact.
